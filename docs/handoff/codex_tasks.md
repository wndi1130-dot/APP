# 코덱스 작업 목록: S1 준비물과 레퍼런스

작성: 2026-10-05 · 상태: 넘김 준비

다른 AI 코딩 에이전트(코덱스 등)에게 넘길 작업 명세다. 설계 결정은 docs/에 있고, 이 작업들은 그 결정을 바탕으로 코드 뼈대와 참고 자료를 미리 만든다.

## 사용법

- 코덱스가 이 저장소(https://github.com/wndi1130-dot/APP)를 읽을 수 있으면 한 줄이면 된다.
  > `docs/handoff/codex_tasks.md`의 공통 규칙을 지키면서 [A1] 작업을 해줘.
- 저장소를 못 읽는 환경이면 '공통 규칙'과 해당 작업 블록을 통째로 붙여 넣는다.
- 작업마다 바로 붙여 넣을 수 있게 줄인 프롬프트: [codex_prompts.md](codex_prompts.md)
- 1차 결과 검토: [codex_review.md](codex_review.md). 그 결과를 반영한 2차 프롬프트: [round2_prompts.md](round2_prompts.md)
- 순서
  - A(코드)는 차례대로 한다: A1 → A2 → A3 → A4 → A5. 모두 s1/ 폴더를 건드려서 동시에 돌리면 충돌한다.
  - B(레퍼런스)는 서로 독립이라 동시에 돌려도 된다. B1(이름)과 B6(좋아하는 것·싫어하는 것)은 A3보다 먼저 끝나면 좋다.
  - 추천 순서: A1, B1, B2 → A2, B3, B6 → A3, B4, B5, B7 → A4 → A5
  - A4(화면 뼈대)는 코덱스에 맡기지 않는다. 클로드 코드로 나중에 한다(2026-10-05 사용자 결정).
- 인터넷: B 작업은 출처를 달아야 해서 인터넷이 켜진 환경에서 돌린다. 꺼져 있으면 '미확인'만 쌓인다.
- 결과는 PR로 받는다. 사람이 보고 main에 합친다.
- 설계 세션은 docs/만 고치고, 코덱스는 s1/과 ref/만 만든다. 폴더가 겹치지 않아서 충돌이 없다.

## 공통 규칙

1. 먼저 읽는다: README.md, docs/design/decisions.md, docs/prototype/s1_political_prototype.md, docs/prototype/s1_content_guide.md, 그리고 작업마다 적은 문서.
2. docs/는 읽기만 한다. 고치지 않는다(설계 세션이 동시에 고친다).
3. 새 파일은 작업마다 정한 폴더에만 만든다. 코드는 s1/, 레퍼런스는 ref/.
4. 새 브랜치에서 작업하고 PR을 연다. main에 직접 push하지 않는다.
5. 사람이 읽는 글(문서, 데이터의 문장)은 한국어로 쓴다. 코드, 식별자, 커밋 메시지는 영어.
6. 사실에는 출처(URL)를 단다. 확인하지 못한 것은 '미확인'으로 표시한다. 지어내지 않는다.
7. 라이선스를 지킨다. 위키백과 같은 글은 문장을 베끼지 않고 사실만 정리해 출처를 단다. OpenStreetMap 데이터는 ODbL이라 출처 표기와 라이선스 안내를 남긴다.
8. 데이터에 넣지 않는 것: 실제 총기 제조사·모델명, 강제 이송 열차를 흉내 내는 표현, 유명 실존 인물의 이름.
9. 큰 원본 파일(수십 MB 이상)은 커밋하지 않고, 다시 받는 스크립트를 남긴다.
10. PR 설명에 쓴다: 무엇을 만들었나, 어떻게 확인하나(명령어), 남은 문제와 미확인 목록.

## A. 코드 (s1/, 차례대로)

### [A1] S1 프로젝트 뼈대와 콘텐츠 검사기

읽을 것: s1_content_guide.md 1장, 2장, 5장

만들 것

- s1/: Vite + TypeScript 정적 웹 프로젝트(서버 없음). 테스트는 Vitest.
- s1/schema/: 가이드 1.1~1.8의 여덟 종류(profile, character, secret, event, law, deal, place, chronicle)의 JSON Schema(draft 2020-12). 열거값, 개수 범위, 글자 수 제한(가이드 2장: 사건 본문 120자, 선택지 15자, 프로필 한 줄 40자, 인물 소개 3문장, 증언 2문장)을 스키마나 검사기에 넣는다.
- s1/schema/effects.schema.json: 효과 어휘(가이드 1.9)를 열거로.
- s1/schema/content_rules.json: 가이드 2장의 '쓰지 않는 것'과 '세계관의 금기'를 검사 규칙으로.
  - 막는 것: 실제 총기 상표·모델명, 대사 속의 '좀비', 수용소와 강제 이송을 떠올리게 하는 어휘.
  - 경고만 하는 것: 성향을 딱지처럼 붙이는 말(탐욕스러운, 겁쟁이, 야심가 등). '가족'처럼 흔한 말은 막지 않는다.
- s1/tools/validate.ts: 데이터 폴더의 JSON을 스키마, 내용 규칙, 길이 제한으로 검사한다. 어느 파일의 어느 항목이 왜 틀렸는지 사람이 읽기 쉽게 알려준다.
- s1/fixtures/valid/, s1/fixtures/invalid/: 종류마다 통과하는 예와 실패하는 예.

완료 기준: `npm test`가 통과하고, invalid 예는 모두 이유와 함께 실패한다. `npm run validate -- <폴더>`로 아무 데이터 폴더나 검사할 수 있다.

하지 말 것: 게임 로직, 화면.

### [A2] 핵심 로직: 시드 난수, 의회 계산, 효과·조건 해석

읽을 것: s1_political_prototype.md 4장, 7장, 8장, 13장 / s1_content_guide.md 1.9

만들 것 (s1/src/core/, 순수 함수와 타입)

- rng.ts: 시드 고정 난수. 같은 시드면 같은 결과.
- state.ts: 게임 상태 타입. 공동체 처지(온기, 배급, 과밀, 위험 노출), 신임·긴장·공포, 자원, 사람의 상태(살아 있음, 다침, 죽음, 파견 중), 집단 관계와 결속도, 플래그, 진행 중인 거래와 약속.
- council.ts
  - 100석을 집단 인구 비례로 나눈다(최대 잔여법). 아이도 인구로 센다. 세력원은 세력 의석으로 센다.
  - 집단의 실제 표 = 의석 × (열차에 남은 인원 ÷ 전체 인원), 내림. 파견 중인 사람은 빠진다. 비율과 반올림 방식은 상수로 빼서 조정할 수 있게 한다.
  - 결속도: 지도자가 약속한 표 중 실제로 따라오는 비율(0~1). 시드로 재현 가능하게.
  - 통과 기준: 일반 법 51표, 통치 법 67표.
  - 공개 투표면 집단별·지도자별로 누가 어떻게 찍었는지 기록하고, 비밀 투표면 합계만 남긴다(매수한 표를 확인할 수 없게).
- effects.ts: 효과 어휘를 상태에 적용하는 함수와 조건(trigger)을 평가하는 함수. 모르는 효과는 에러로 막는다.

완료 기준: 테스트로 확인한다. 의석 합은 언제나 100, 51·67 경계, 파견 제외, 결속도, 공개·비밀 투표의 기록 차이, 같은 시드 재현.

### [A3] 프로필 200명 데이터 생성기 (문장 제외)

읽을 것: s1_content_guide.md 3.5 / docs/design/briefs/world_lore.md / docs/design/briefs/europe_setting.md

만들 것

- s1/tools/gen_profiles.ts → s1/data/profiles.json. line 필드는 빈 문자열로 둔다(문장은 A5에서 채운다).
- 규칙(가이드 3.5)
  - 공동체 인원: 꼬리칸 90, 앞칸 30, 기술·의무진 30, 경비대 25, 기관실 25.
  - 아이(0~15세) 약 15%. 첫 런은 붕괴 후 여섯 번째 겨울이라, 열차에서 태어난 0~5세가 있다.
  - 노인(65세 이상) 약 10%. 기관실은 나이 많은 쪽으로.
  - 탄 경위는 공동체별 기본 줄기에 20%쯤 다른 경위를 섞는다.
  - 고향은 폴란드·독일·체코 중심, 피난민은 더 넓게.
  - 가족 묶음: 같은 공동체 안의 부모, 자식, 형제.
- 이름은 ref/names/(B1)가 있으면 쓰고, 없으면 작은 임시 목록을 쓴다. 좋아하는 것·싫어하는 것은 ref/likes_dislikes.json(B6)이 있으면 쓴다.
- 같은 시드면 같은 200명이 나온다.

완료 기준: A1 검사기를 통과한다. 분포 테스트(공동체 인원, 나이 비율, 경위 비율, 가족 묶음)가 통과한다.

### [A4] S1a 화면 뼈대 (더미 데이터) · 클로드 코드로 할 예정

읽을 것: s1_political_prototype.md 2장, 3장, 15장 / docs/design/briefs/presentation_ui.md

만들 것

- 폰 가로 화면 레이아웃. 그래픽 없이 도형과 글자만 쓴다.
  - 홈: 가로로 그린 열차 띠(2D 칸 상자). 칸마다 공동체 이름과 상태 색(온기, 과밀).
  - 칸을 누르면 그 칸의 화면이 열린다: 식당칸은 의회, 열차장실은 일지와 인물.
  - 가운데 맨 위: 불만·지지 띠. 누르면 집단별로 펼쳐진다.
  - 상단 한 줄: 신임, 긴장, 석탄·식량·의약품·사치품.
  - 아래 양쪽 모서리: 조작 버튼(엄지 자리). 결정 카드는 아래에서 올라온다.
  - 의회: 반원 100석, 집단별 찬성·반대·미정.
- 한 구간의 다섯 단계(출발 전 운영 → 이동 → 정차 → 의회 → 정산)를 차례로 넘기는 흐름. 의회는 3구간마다.
- 기능 플래그(S1a, S1b, S1c), 저장 한 슬롯(localStorage, 시드 포함), 숨은 수치를 보는 디버그 화면.
- 세로로 들면 "가로로 돌려 주세요"를 보여준다.

완료 기준: 844×390 뷰포트에서 가로 스크롤 없이 보인다(Playwright 스크린샷을 PR에 첨부). A2의 core를 가져다 쓰되, 게임 규칙은 아직 더미여도 된다.

### [A5] Gemini 문장 생성 파이프라인

읽을 것: s1_content_guide.md 0장, 2장, 4장, 5장

만들 것

- s1/tools/gen_text.ts: 데이터 JSON에서 문장 필드(line, bio, body, 선택지 label, preview 등)가 빈 항목을 찾아 Gemini로 채운다.
  - 요청 조립: 고정 지시(가이드 2장과 세계관 금기), 그 항목의 데이터 JSON, 예시(가이드 3.2), 출력 형식(JSON만).
  - 결과는 A1 검사기를 통과해야 저장한다. 실패하면 실패 이유를 붙여 다시 요청한다(횟수 제한).

  - 비용 보호: 한 번에 채울 항목 수 제한, 요청만 만들어 보여주는 드라이런 모드.

완료 기준: 테스트는 가짜 응답(mock)으로 돈다. 드라이런으로 만든 요청 예시를 PR에 붙인다.

## B. 레퍼런스 (ref/, 동시에 돌려도 됨)

### [B1] 이름 풀과 한글 표기

만들 것

- ref/names/pl.json, de.json, cz.json, other.json: 이름(남·여)과 성. 폴란드어·체코어 성은 남녀 형태를 모두 넣는다. 언어마다 이름 150개 이상, 성 200개 이상. other는 피난민용(우크라이나, 슬로바키아, 헝가리, 리투아니아 등)으로 조금.
- 항목마다 원어 표기와 한글 표기.
- ref/names/transliterate.(ts|py): 국립국어원 외래어 표기법(폴란드어, 독일어, 체코어 표기 세칙)을 따르는 변환기와 테스트. 테스트 사례는 국립국어원 용례에서 가져오고 출처를 단다. 예상 예시(규칙으로 확인할 것): Leipzig → 라이프치히, Krejčí → 크레이치, Mazurek → 마주레크.
- ref/names/famous_blocklist.json: 각국 유명 실존 인물의 이름+성 조합 수백 개. 생성기가 이 조합을 피하게 한다. 출처 표기.
- 흔한 이름의 출처(각국 통계청 등)는 ref/names/README.md에.

완료 기준: 변환기 테스트가 통과하고, 모든 항목에 한글 표기가 있고, README에 출처와 방법이 있다.

### [B2] 좀보이드 캐릭터 생성 체계 레퍼런스

목적: 다음 설계 주제(열차장 캐릭터 생성: 좀보이드식 스탯, 특성, 피지컬)의 근거 자료.

만들 것: ref/zomboid_character_creation.md

- 현재 안정판(B42) 기준으로 정리한다: 직업과 시작 보너스, 특성(긍정·부정과 점수), 기술 목록과 오르는 방식, 신체 스탯(근력, 체력, 체중 등)과 플레이 중의 변화. 표로.
- B41과 B42가 다른 곳은 표시한다.
- 플레이 중 특성이 생기고 사라지는 모드(Dynamic Traits and Expanded Moodles 등)의 요지.
- 출처: 공식 위키, 공식 패치 노트, 모드 페이지 URL.
- 끝에 '우리 게임에 옮길 때 생각할 점'을 짧게 적는다: 모바일, 외울 게 적게, 우리 지식 분야 5개(기관, 의료, 공작, 통신, 원정)와 보류 중인 필드 능력 초안(근접, 사격, 은신, 체력, 수색)과의 관계. 결정은 하지 않는다.

### [B3] 증기기관차 운용 레퍼런스

만들 것: ref/steam_operations.md

- 승무원(기관사, 화부)의 일과 분업.

- 끝에 '게임과 닿는 곳'을 적는다: 석탄 경제, 제설 쟁기, 증기 공기총 충전, 기관 지식(견습·숙련·장인)과 연결되는 사실.

### [B4] 실제 철도망 데이터 (핵심 지역)

범위: 폴란드 서부, 독일 동부, 체코, 그리고 슈트랄준트와 뤼겐섬.

### [B5] 장소 유형 레퍼런스 (중부 유럽)

만들 것: ref/places_central_europe.md, ref/places_loot_draft.json

- 장소 유형 여섯(화물역, 주택가, 병원, 공장, 교회, 관청)이 폴란드·독일·체코에서 실제로 어떤 모습인지: 건물 형태, 흔한 배치, 지역색(예: 조립식 아파트 단지, 가톨릭 성당과 루터교 교회의 차이).
- 그 안에 있을 법한 물건을 우리 자원(석탄, 식량, 의약품, 사치품, 상징물, 정보 문서)으로 나눠 정리한다. 위험 요소와 상징물 후보(깃발, 종, 사진 등)도.
- places_loot_draft.json은 콘텐츠 가이드 1.7(장소 스키마)의 loot와 symbols 초안이다.
- 출처 표기.

### [B6] 좋아하는 것·싫어하는 것 풀

만들 것: ref/likes_dislikes.json

- 중부 유럽 사람이 좋아하거나 싫어할 법한 것: 옛 세상의 물건, 음식, 소리, 습관, 사람, 장소. 갈래마다 150개 이상.
- 한국어로, 15자 이내.
- 태그: 나이대, 어울리는 공동체, 고향 나라, 계절(한파, 해빙기), 지금 세계에서 구할 수 있는지(가끔 사건에 걸리게).
- 상표명과 실존 인물 이름은 넣지 않는다.

### [B7] 대사 레퍼런스 분석 노트

목적: 사건 카드, 의회 대사, 증언을 쓸 때 참고할 기법을 정리한다. 대본을 모으는 작업이 아니다.

대상: s1_content_guide.md 2장 '참고 작품' 표의 작품들.

만들 것: ref/dialogue_references.md

- 작품마다 적는다.
  - 우리 게임의 어디에 쓰나: 사건 카드, 의회 대사, 증언, 무전, 프로필 한 줄 중에서.
  - 기법 3~5개: 문장 길이, 시점, 선택지 문구를 짓는 방식, 정보를 숨기고 드러내는 법, 말투로 계급을 드러내는 법.
  - 그 기법을 우리 세계로 옮긴 예문. 우리가 새로 쓴 문장이어야 한다.
- 인용은 작품마다 최대 2~3군데, 한 번에 한두 문장만, 출처를 단다. 대본 전체나 긴 대목은 옮기지 않는다(저장소가 공개다).
- 공식 한국어판이 있는 작품은 번역투로 보이는 표현을 따로 모은다(피할 말 목록).
- 결정은 하지 않는다. 문체 가이드에 넣을 후보만 끝에 모은다.
