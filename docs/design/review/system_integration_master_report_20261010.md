## 0. 범위·판정·읽는 법

### 0.1 이번에 실제로 한 일과 하지 않은 일

GitHub의 커밋 차이, 주요 실행 코드, 데이터 정의, 설계 브리프, 핸드북, 진행 중 PR을 읽었다. 이전 검토 이후 첫 기준까지 27개 커밋, 정독 중 추가된 최종 기준까지 10개 커밋의 차이를 대조했다. 주요 분석 대상은 정치·내정 훅, 기술·법, 상징물, 인물, 위생, 필드 진입점, 무리 감독, 눈 상태, S3 이식 도구와 신규 브리프다. [R01][R02][R03][R04]

**저장소 전체를 실행하거나 모든 경로를 완전 탐색하지 않았다.** GitHub에 올라오지 않은 로컬 변경, 비공개 아트 원본, 실제 휴대폰 플레이·프레임·발열은 이번 검토에 포함되지 않는다. 저장소 테스트 전체도 재실행하지 않았다. 본문 18장의 세 검사는 읽은 계산을 작은 독립 예제로 옮겨 실행한 것이며, 앱의 종단 간 재현과 다르다.

이 보고서는 게임 코드를 수정하지 않는다. 제안의 수치와 제작 순서는 별도 채택·구현·검증 대상이다. 기존 문서의 확정 사항을 이 보고서만으로 바꾸지 않는다. 특히 **현재 기준 뒤에 합쳐진 작업을 미구현이라고 단정하지 않도록 커밋을 고정**했다.

## 1. 바꾸지 않을 게임의 정체성과 최신 결정

**밖에서 내 손으로 구해 온 것으로, 안에서 내가 책임지는 사회를 바꾼다. 그 사회가 다음에 밖으로 나갈 사람과 방법을 바꾼다.**

사용자가 원하는 것은 기능을 많이 넣은 메뉴 모음이 아니다. 위험을 감수한 수색, 물건과 사람의 귀환, 눈에 보이는 열차의 변화, 이해관계가 있는 정치, 다음 정차의 새로운 가능성이 이어지는 게임이다. 매우 어둡지만, 충분한 준비와 어려운 합의를 통해 사람을 소모품으로 다루지 않고도 버틸 길을 열어 둔다. 인간찬가는 쉬운 선행 버튼이나 무사망 보너스가 아니라 **좋은 원칙을 실제로 지킬 능력을 만든 결과**다.

## 2. 현재 프로젝트에 대한 총평

### 2.1 이미 의미가 생긴 부분

정치·내정·필드가 모두 문서에만 있는 상태는 아니다. 내정 정산에서 공방·지식·위생·상징물·침상 등이 호출되고, 기술 효과에는 관련 법 조건이 붙으며, 필드는 몸·소리·위협·귀환 결과를 다룬다. 이 연결을 지우고 새 프레임워크로 갈아엎을 이유가 없다. [R06][R07][R10][R14][R15]

특히 다음은 이전의 ‘없다’는 평가를 그대로 반복하면 안 된다.

| 기능 | 확인한 진전 | 아직 별도로 확인할 것 |
|---|---|---|
| 상징물 | 걸기·내리기·정산 효과가 실제 코드에 들어갔다 | 물건의 고유성, 손실 대상, 사용 장면과 역사 |
| Godot 정치 이식 | 난수·표 계산 등 기초 모듈과 비교용 자료가 생겼다 | 열차 상태를 들고 필드를 왕복하는 전체 S3 |
| R3 장거리 무전 | 결과 없는 소비를 막는 `NOT_YET` 가드가 있다 | 미래 정보·노선 선택 소비자가 생긴 뒤 해제 |
| 기술의 쓸모 안내 | 적용 법과 현재 여부를 알리는 문구·조건이 있다 | 시설과 생활에서 그 차이가 보이는가 |
| 위생 | 원인 설명, 초기 유예, 예방 상태, 재발 유예가 있다 | 다른 사건까지 같은 원인-해결 모델로 일관되는가 |
| 무리 | 소음 당김, 소탕 뒤 휴지기, 진입 경로가 있다 | 무한 압박의 이유와 플레이어가 번 시간의 체감 |
| 눈 | 깊이·새로 쌓인 양을 계산해 표현에 넘기는 코드가 있다 | 모델·장면과의 통합, 최신 ‘그림만’ 계약 |
| 조작·몸 화면 | 조작 개선과 몸 패널 작업이 진행됐다 | 실제 손맛·읽기 쉬움은 폰 확인 필요 |
| 추가 브리프 | 교실·무전·위임·음식·썰매·진화·의수의 빈칸을 별도 문서로 메우고 있다 | 코드가 생겼다는 뜻은 아님. 문서끼리도 시간·인원·자원 계약을 맞춰야 함 |

정독 시작 때 열려 있던 상태 아이콘 PR #128의 변경 범주는 최종 대조 범위의 `body_state.gd`, `field_hud.gd`, 테스트 변경에도 반영되어 있다. 아이콘을 다시 ‘없는 기능’으로 제안하지 않는다. 그 PR에 적힌 테스트 이력은 작성자의 보고이지 이번 검토의 실행 결과가 아니다. [R04][R30]

### 2.2 붕 뜨는 기능의 다섯 종류

**소비자가 없는 상태**는 쓰일 자리가 생길 때까지 잠그거나 연결한다. `captainInBed`, R3처럼 단계상 비어 있는 곳은 무조건 지울 대상이 아니다.

**효과는 있지만 이유가 약한 상태**는 원인을 고친다. 대표 사례가 상징물의 자동 결속, 교사의 공동체에 따른 효율 절반, 정직성에 따라 달라지는 음식 환산의 설명이다.

**다른 시스템과 같은 일을 두 번 하는 상태**는 책임을 분리한다. 직접 필드의 실제 부상과 자동 정차의 사망 추첨을 귀환 뒤 겹치면 안 된다.

**결정이 아닌데 조작을 요구하는 상태**는 자동 처리하고 결과만 보여 준다. 미미한 조리 환산 이득이나 늘 같은 승인에 카드 한 장을 쓰지 않는다.

**변화를 만들어도 플레이어가 볼 수 없는 상태**는 연출과 다음 행동에 연결한다. 개선한 시설을 주민이 실제로 사용하는 장면이 대표적이다.

따라서 결론은 ‘의미 없는 기능을 전부 삭제하자’가 아니다. **독립 메뉴·독립 게이지·독립 보상으로 떠 있는 기능의 지위를 내려놓고, 기존 선택의 원인·수단·결과 중 하나로 넣자**는 것이다.

## 4. 먼저 손볼 실제 판정과 공통 계약

### 4.1 A01 — ‘그들이 고른 복원’과 ‘그들이 좋아하는 복원’은 다르다

`domesticPromise()`의 `research_pick` 분기는 기간 안의 복원 기록에서 해당 공동체가 좋아하는 기술이 있는지 검사한다. 현재 지정 대상인 `d.researchPick`와 비교하지 않는다. 기록에 `v`가 있지만 이 분기의 선호 검사에는 실제 고른 변형을 직접 사용하지 않는다. [R07][R12]

**함수 수준 예시:** 지정 대상이 `m1`인데 `w1`을 시작해도, 둘 다 기술·의무진 선호 기술이므로 현재 조건식은 이행으로 본다. 실제 UI가 다른 복원 시작을 어느 지점에서 막는지까지는 검증하지 않았다. 따라서 이것은 ‘모든 판에서 사용자가 악용할 수 있다’는 재현 보고가 아니라 **이행 판정 자체가 계약의 대상을 보증하지 못한다는 지적**이다.

권고는 약속을 만들 때 다음을 고정하는 것이다.

```text
promise_id
promisor_id / beneficiary_id
action_kind
subject_id / agreed_variant
created_at / due_at
required_evidence
status: pending | fulfilled | broken | renegotiated
```

`research_pick`는 합의한 기술의 시작인지, 완성인지부터 명시한다. 시작이 약속이면 완성까지 요구하지 않는다. 변형까지 약속한 경우에만 변형도 비교한다. 사후에 다른 기술을 골랐다고 기록을 해석해서 맞춰 주지 않는다.

### 4.2 A02 — 약속을 제시하는 쪽도 실행 조건을 알아야 한다

`researchChoice()`는 아직 손대지 않은 기술 중 선호와 단계만으로 후보를 고른다. 반면 실제 복원은 `restoreCheck()`가 R3 잠금, 선행 기술, 숙련, 조각, 코어, 부품, 공방 점유를 검사한다. [R07][R09]

`m1`, `m2`, `w1`이 이미 있는 예에서 후보 함수는 `r3`를 반환하지만 복원 함수는 R3를 막는다. 이 역시 독립 함수 예시이며 실제 약속 제안의 전체 도달성은 미확인이다.

조건은 셋으로 나누는 것이 낫다.

- **지금 가능:** 바로 실행할 수 있는 선택.
- **기한 안 준비 가능:** 현재는 부족하지만 알려진 조달·작업 계획이 있다. 플레이어가 그 불확실성을 보고 약속할 수 있다.
- **현재 버전에서 불가능:** 기능 자체가 잠김. 약속 후보가 되어서는 안 된다.

모든 약속을 ‘지금 재고가 충분한 것’으로만 제한하면 조달 약속의 재미도 없어진다. 반대로 구현되지 않은 기능까지 정치 약속으로 팔아서는 안 된다.

### 4.3 A03·A04 — 문장이 규칙을 결정하거나 사실을 만들어내지 않게 한다

`again()`은 과거 선택의 표시 문구로 후속 문장을 고른다. 문장을 손보는 작업과 상태 이관이 불필요하게 묶이는 구조다. 고정 선택 ID를 도입하고 이전 문구는 저장 버전에 따른 매핑으로 한 번만 옮긴다. [R13]

또한 대사의 ‘아이 몇 명’, ‘누가 돌아오지 않았다’, ‘지난번 약속’에는 실제 근거가 필요하다. 현재 `kids()`는 인구 비율과 최소 2를 쓰므로 실제 아이 명부가 아니다. 인구 0을 넣으면 2를 반환하지만, 그런 공동체에 해당 카드가 뜨는지는 별도 조건을 확인해야 한다. 이 차이를 구분해 기록한다.

**규칙:** 실제 개별 인원을 언급할 때는 명부를 읽는다. 집단 수준 추정만 존재하면 ‘아이들이’처럼 범위에 맞는 표현을 쓴다. 이야기 효과를 위해 인물 사망을 본문만으로 발생시키지 않는다. 반대로 실제 사망이 있으면 개인·가족·직책·침상·일대기의 소비자가 같은 사실을 받아야 한다.

### 4.4 A05·A11 — 같은 사람의 여러 역할을 연결한다

현재 전문가 표현과 대표 표현이 별도로 존재하는 것은 시제품의 합리적인 출발이다. 하지만 S3에서는 이름 일치에 의존해 연결하지 않는 것이 좋다. [R12]

```text
Person: 같은 사람의 고정 ID
Roles: 대표 / 공방장 / 교사 / 무전수 / 수색대원 등
Presence: 열차 안 / 현장 / 파견지 / 위치 미확인
Life: 생존 / 사망 확인 / 불명
Medical: 상처·회복·보조기 등
WorkAssignment: 어떤 시간에 어떤 일에 배치되었는가
Knowledge: 전문 지식·전수 이력
```

역할이 바뀌어도 사람은 같은 사람이다. 대표가 아프면 발언 대행은 바뀔 수 있지만 그 사람이 지닌 관계·가족·기억이 새로운 대표에게 자동 복사되지는 않는다. 죽거나 실종된 사람을 똑같은 이름의 대체 인물로 채워 넣지도 않는다.

`captainInBed`는 이 구조의 소비자로 삼는다. 필드의 실제 부상에서 열차장 가용성이 바뀌고, 승인된 운영은 계속되며, 새롭고 중대한 선택은 기존 승인 규칙에 따라 처리한다. 예약된 연결점을 삭제하는 것보다 의미를 채우는 것이 맞다.

## 5. 기능별로 ‘무엇에 붙여야 의미가 생기는가’

### 5.1 상징물: 결속 아이템에서 생활의 물건으로

현재 상징물은 걸어 둔 공동체의 결속을 구간마다 0.01 올리고, 내리거나 잃으면 결속 0.08·관계 4를 깎는다. 숫자는 현 코드의 값이지 이번 권고 값이 아니다. 총개수가 줄면 최근에 걸었던 공동체부터 해제한다. [R05]

이는 작동하는 메커니즘이지만, ‘내가 어느 역에서 누구와 함께 가져온 종’은 표현하지 못한다. 상징물을 없앨 것이 아니라 개별 자산으로 확장한다. 새 식별자가 들어가기 전의 저장은 고유한 이전 자산으로 이관하되, 모르는 출처를 지어내지 않는다.

**연결:** 발견 → 운반 → 배치 → 실제 사용 → 관련 사람의 기억 → 상태에 따른 반응. 손실은 실제 그 물건의 손실이어야 한다. 공짜 재설치 보상, 같은 물건 반복 생성, 이유 없는 다른 칸의 피해는 막는다. 결속 효과를 즉시 없애는 재밸런싱과 자산 식별자 이관은 분리한다.

### 5.2 기술·법: 설치했지만 못 쓰는 이유가 보이게 한다

법 조건과 기술 쓸모 안내는 이미 있다. ‘기술이 쓸모없다’고 일반화하지 않는다. 다만 기술을 얻었을 때 화면에는 물건이 생겼는데 아무것도 작동하지 않으면, 법 조건을 읽지 않은 사용자는 버그로 느낄 수 있다. [R10]

시설은 **미확보 / 공사 중 / 설치 완료 / 가동 / 공급·인력 부족 / 실제 고장**을 구분한다. 이미 있는 추인 대기를 모든 기술에 새 표결로 확장하지 않는다. 해당 법에 묶인 기술만 그 법의 효과를 바꾸고, 그 변화가 객차의 사용 모습으로 나타나게 한다.

예컨대 난방 배관은 단순한 ‘온기 +숫자’가 아니라 실제로 이용하는 칸과 비용·배분을 바꾼다. 완성했지만 법이 적용되지 않으면 배관은 남고 사용 상태만 다르다. 폐지했다고 완성한 장치 자체가 사라지는 연출은 피한다.

### 5.3 무전: 생존 확률 보너스에서 정보·협력 능력으로

자동 정차의 R1 사망 배율은 추상 결과를 만드는 방법이다. 직접 필드에서 같은 숫자를 그대로 사후 적용해서 이미 죽은 사람을 살리거나, 살아 돌아온 사람의 사망을 다시 추첨해서는 안 된다. [R06]

직접 모드에서는 예고·호출·연락·합류 확인 같은 실제 수단으로 나타나게 한다. 자동 모드는 그 수단을 얼마나 갖추었는지 결과 모델에 반영한다. 결과의 분포와 경제적 가치는 비교하되, 양쪽 결과가 항상 같아야 한다고 요구하지 않는다.

기본 R1 이전 연락과 R1 이후 향상의 관계부터 고정해야 한다. S2의 기본 예보는 이미 방향을 말한다. 중거리 무전의 보상은 ‘처음으로 방향을 알게 됨’이 아니라, 출처가 확인된 추가 정보·예보 해상도·연락 유지 같은 별도 차이로 정의하는 쪽을 권한다. 새 성능은 모두 제안이며 H3의 기본 경고를 몰래 후퇴시키지 않는다. [R15][R20]

### 5.4 교실: 미래 보상만 기다리는 장식이 아니게 한다

최신 문서가 캠페인과 세대 효과를 나눈 것은 타당한 정리다. 캠페인에서는 학습·매뉴얼·교사의 실제 시간과, 사람들이 가르칠 자리를 유지하는 모습이 지금의 가치다. 성인 진입·세대 이념은 실제 긴 시간이 흐르는 무한모드에서 다룬다. [R20]

두 명세는 보완이 필요하다. 교사가 기관실 출신이라는 이유만으로 글과 셈을 절반밖에 못 가르치게 하지 않는다. 실제 능력·경험·교재·동의하지 않아 생긴 행동을 읽어야 한다. 그리고 아이가 열차 안에서 짐을 꾸린다고 수업과 동시에 할 수 있는 것은 아니다. **위치가 같다는 것과 시간이 겹치지 않는다는 것은 다르다.**

교육의 이점 때문에 아이를 사실상 즉시 공방 숙련자로 바꾸는 것도 피한다. 성인 견습에게 읽기·셈 교육을 적용할 경우에도 대상과 수업 시간이 명확해야 한다. 새로 아동 필드 행동을 확대하지 않는다.

### 5.5 위임: 없던 수동 작업을 만들어 자동화하지 않는다

경비대장은 이미 필요한 원정·작업조 명단을 준비하므로 의미가 크다. 의무장과 기관장은 새 화면을 만들기 전에 기존 상태에서 무엇을 추천·유지·경고할지 정한다. [R21]

명단의 기본값은 유용해야 하지만, 사람의 중대한 위험·치료·교사 선발 같은 기존 확인 경계는 유지한다. 반복되는 승인된 배급·수리는 계속 돌아가고, 원칙을 벗어나는 예외만 올라온다. 관계가 나빠져 위임이 풀려도 기존 설정이 사라져 모든 화면을 다시 만지게 하지 않는다.

의무장의 비축 하한과 긴급 치료가 충돌하면 숨은 자동 거절로 끝내지 않는다. 어떤 원칙 때문에 누가 치료를 못 받는지 보여 주고, 권한 안의 예외를 물어야 한다. 기관장과 배급장이 같은 석탄을 각각 썼다고 가정하지 않도록 공동 자원 예약을 둔다.

### 5.6 음식: 양·몸·정직성은 다른 축이다

조리의 방향과 불리기 수단은 최신 사용자 결정을 유지한다. 식량 재고는 귀환 후 하나의 숫자로 남기며, 개인별 냉장고·재고 회전 메뉴를 새로 만들지 않는다. 아래는 게임 규칙 감사이며 실제 음식 제조·안전 지침이 아니다. [R23]

명세에서 분리할 것은 네 가지다.

1. **받아들인 실제 식량 가치:** 출처와 상태를 어떻게 환산하는가.
2. **처리 작업과 비용:** 실제 더운물·작업·연료를 언제 얼마나 쓰는가.
3. **배급의 물리적 결과:** 같은 방식과 같은 양이면 몸에 같은 영향을 주는가.
4. **공개·은폐의 정치적 결과:** 누가 알고, 무엇을 공표했고, 어떤 약속을 어겼는가.

현재 제안 표는 몰래 섞기와 밝히고 섞기에 서로 다른 절약 배율을 둔다. 공개 배급에서 실제 다른 방식·한도를 쓰기 때문이라면 명시하면 된다. **단지 정직하게 말했다는 이유로 같은 물건의 물리 환산이 달라져서는 안 된다.** 공개는 기만의 책임을 바꾸지만 몸의 대가를 지우지는 않는다.

더운물 레버를 귀환 직전에 올리고 환산 직후 내리면 처리 비용 없이 이득을 얻는 명세가 되어서는 안 된다. 한 번의 귀환 처리에 필요한 비용을 확정하거나 실제 작업 시간으로 정산한다. 시든 물건 몇 개의 작은 환산 차이는 자동으로 처리하고 솥 장면·짧은 장부 줄로 보여 주는 편이 낫다. 이득이 작다는 이유로 조작 횟수를 늘리지 않는다.

몰래 섞은 사실은 실제 실행자와 관련 보고에 남는다. 공개로 전환해도 과거 기록을 삭제하지 않는다. 다만 동일한 행위에 건강·기만·약속 위반·공동체 관계 벌을 각 모듈이 아무 조정 없이 중복 청구하지 않게 한다.

### 5.7 썰매: 더 많은 사람을 내보내는 의미를 보존하면서 왕복을 줄인다

12짐·20짐과 사람 몫을 대체하지 않는 원칙은 유지한다. 가치가 있어야 하는 곳은 **짐을 한 번에 옮기는 시간, 무기를 못 드는 시간, 어디에 세울지, 실제 바닥에서의 이동**이다. [R24]

단, ‘담을 수 있는데 이유 없이 더 가져올 수 없음’으로 보이지 않게 해야 한다. 인원별 회수 총량·작업 허용량이 추상 계약이면 준비 화면에서 그것을 밝혀야 한다. 지도를 괜히 길게 늘려 썰매의 존재 이유를 만들거나, 같은 상자 왕복을 강제해서 편의 장비를 팔지 않는다.

썰매 줄 놓기는 즉각적이고 명령 취소는 예측 가능해야 한다. 주운 물건·내려놓은 물건·썰매·승강장 적재가 소유권을 공유해야 한다. 최신 결정상 자국은 시각 효과뿐이며, 사람이 자국을 추적한다는 기존 문장은 정리 대상이다.

추가로 S1의 X3 궤도 모터카 추상 산출과 출시판 운반 수단 범위는 용도를 구분해야 한다. 추상 정차 기술의 시제품 효과를 실제 운전 가능한 차량이 이미 출시 범위에 들어온 것처럼 해석하지 않는다. [R07][R24]

### 5.8 위협·눈·진화: 이미 번 시간을 시스템이 인정해야 한다

무한 무리 자체는 확정 방향이다. 없애자는 제안이 아니다. 현재 감독은 시간 기반 간격 축소, 소음 당김, 소탕 휴지기를 가진다. [R15]

플레이어에게는 ‘정차한 열차를 향해 계속 모이는 압력’과 ‘내가 큰 소리를 내서 더 빨리 온 압력’이 구분되어야 한다. 조용히 했는데 무리가 오는 것이 규칙 위반은 아니지만, 조용히 한 결과가 무엇인지 체감할 수 있어야 한다. 기존 간격·최소 간격과 소음 규칙을 먼저 계측하고, 좋은 플레이의 여유를 다른 이벤트로 몰래 회수하지 않는다.

열 쫓는 자와 부르는 자는 기존 열·무리 상태의 소비자다. 별도 보일러 손잡이는 유지하면서, 같은 불 세기가 난방·연료·유인·출발 준비에 연결되게 한다. 부르는 자의 제한 단위는 ‘한 방문’인지 ‘한 무리 시계’인지 명확히 고정하고, 중복된 지연·당김을 같은 무리 ID로 통제한다. [R22]

눈은 현재 깊이와 새로 내린 양을 구분하는 기반이 있다. 여기서 발자국·끌린 자국을 그림으로 표현할 수 있다. 하지만 이번 버전에서는 그 자국 때문에 적의 감지가 좋아지거나 이동 저항이 새로 생기지 않는다. **진짜 바닥·소리 규칙과 장식 흔적은 명확히 나눈다.** [R16][R25]

## 6. 하나의 거대한 시스템으로 묶는 여섯 순환

여기서 ‘거대하다’는 모듈이 많은 것보다 **서로의 결과가 돌아오는 범위가 넓다**는 뜻이다.

| 순환 | 한 바퀴 | 플레이어가 알아야 할 인과 |
|---|---|---|
| 물자와 생활 | 부족 → 장소 선택 → 수색·작업 → 재고 → 시설·배분 → 다음 필요 | 무엇을 구했기 때문에 어떤 생활이 가능해졌나 |
| 노동과 지식 | 인원 배치 → 노출·부상·휴식 → 견습·대행 → 능력·교대 여력 → 다음 명단 | 같은 사람을 덜 소모할 방법을 만들었나 |
| 정보와 정치 | 관측 → 보고·소문·검증 → 발언·약속 → 표결·책임 → 다음 정보 접근 | 누가 무엇을 알고 왜 그렇게 주장하나 |
| 열과 위험 | 불 세기·배분 → 온기·소비 → 작업·체류 → 위협·철수 → 수리 여력 | 편안함과 안전, 체류와 출발의 값을 어떻게 나누나 |
| 물건과 기억 | 발견 → 소유·배치 → 사용 → 관계와 생활 → 이후 손실·회복 | 같은 물건이 내 열차에서 무엇이 되었나 |
| 장소와 장기 목표 | 방문 → 회수·수리·남김 → 지속 상태 → 재방문·소식 → 캠페인·무한모드 선택 | 세상과 열차가 내가 지나간 뒤 달라졌나 |

### 6.1 실제 통합의 중심은 다섯 종류의 사실이다

**물자가 이동했다. 사람이 어떤 일을 했다. 누군가 어떤 일을 알게 됐다. 약속이나 규칙이 실행됐다. 장소나 시설의 상태가 바뀌었다.**

모든 기능이 새 수치를 하나씩 만드는 대신 이 다섯 사실 중 무엇을 만들고 무엇을 읽는지 적는다. 예를 들어 교실은 지식·시간·공간을 읽고 학습·생활 이력을 남긴다. 의회는 처지·약속·정보를 읽고 허용된 배분과 권한을 바꾼다. 연출은 같은 결과를 보여 주지만 경제를 다시 계산하지 않는다.

### 6.2 모듈 소유권

| 모듈 | 단독으로 쓰는 상태 | 다른 모듈에 주는 결과 |
|---|---|---|
| 인물 | 동일성·생사·가용성·역할·능력 | 배치 가능한 사람, 관계의 당사자 |
| 자원 장부 | 재고·예약·이동·소비 | 확정된 비용과 실제 입출고 |
| 작업·시설 | 공간 점유·작업 진행·설치·가동 | 제공한 열·생산·치료·교육 등의 서비스 |
| 원정 해석기 | 한 방문의 이동·전투·수색·철수 | 실제 또는 추상화한 정차 결과 |
| 정치 | 의회·법·거래·약속·책임 | 승인된 제약과 이행 판정 |
| 지식·정보 | 관측·전달·검증·학습 | 누가 아는 내용과 실행 가능한 기술 |
| 문제·이야기 | 원인별 문제·보장 사건의 조건 | 해결되지 않은 선택, 후속 사건 후보 |
| 세계 | 장소 변경·시간·노선·장기 상태 | 방문 맥락과 지속 결과 |
| 표현 | 화면·동작·소리·문장 선택 | 플레이어가 읽는 결과. 경제·사망의 원천이 아님 |

지금의 `Game`/필드 구조를 전부 버리고 이 표대로 새 엔진을 만들자는 뜻은 아니다. 기존 상태와 함수에서 소유자를 명확히 하고, 경계를 넘는 입력·출력부터 고정한다.

## 7. 공통 상태·이벤트 계약 — C01~C14

### C01. 표시 이름과 동일성을 분리한다

사람·물건·객차·방문·선택·약속·문제에 고정 ID를 둔다. 번역, 개명, 직책 변경, 객차 이동으로 ID가 달라지지 않는다. 기존 저장의 모르는 출처는 ‘기록 없음’으로 남긴다.

### C02. 명령은 한 번 검사하고 결과를 한 번 확정한다

```text
플레이어/승인된 간부 명령
→ 가능 조건·권한·자원 예약 검사
→ 해당 규칙 계산
→ 상태와 사실 기록 확정
→ 관련 모듈의 후속 처리
→ 표현 선택
```

버튼·애니메이션 종료·귀환 화면이 각자 자원을 더하지 않는다. 중요한 입력에는 요청 ID와 상태 버전을 붙여 중복 실행을 막는다.

### C03. 직접 정차와 자동 파견은 동일한 결과 계약을 쓴다

동일한 출발 명단·장소 기회·장비·승인 원칙을 입력받는다. 직접 모드는 플레이어 행동을, 자동 모드는 능력과 원칙을 해석한다. 결과는 같은 검증기로 확인하고 한 번만 정산한다. 자동 파견에만 존재하는 무근거 보너스나 직접 모드 뒤 추가 사망 추첨을 금지한다.

### C04. 출발 명세와 귀환 결과를 구분한다

현재 영수증을 버리지 말고 외부 봉투 또는 다음 명시적 버전으로 확장한다. 아래는 구현 완료 스키마가 아니라 필요한 의미 항목이다. [R14]

```text
출발 명세:
  visit_id, manifest_id, rules_version
  장소 ID와 당시 알려진 정보
  실제 출발 인물 ID, 역할, 장비, 승인된 원칙
  배정 자원과 소유권 이전 내역
  출발 시점과 현재 상태 버전

귀환 결과:
  visit_id, manifest_id, result_id, source(direct/auto)
  도착·출발 게임 시각
  인물별 실제 이동·몸·생사 변경
  물건별 획득·소비·분실·적재 내역
  관측 사실과 보고 가능한 내용
  장소 변경
  약속 이행의 증거 참조
```

현재 영수증의 `sent`, `injured`, `rescued`, `dead` 등은 서로 배타적인 한 상태 목록이 아니다. 보냈던 사람이 다쳐 돌아올 수 있고, 구조한 사람이 부상자일 수 있다. **생사·위치·의료 상태를 직교하게 모델링**하고 모순만 막는다.

### C05. 동일한 귀환은 정확히 한 번 반영한다

`result_id` 처리 기록과 인물·재고·장소 변경을 함께 확정한다. 중간에 앱이 종료되면 완료된 상태를 읽거나 미완료 트랜잭션을 복구한다. 일부만 적용한 뒤 재시도로 두 번 더하지 않는다. 저장 구조는 16장에서 다룬다.

### C06. 자원은 장부 한 곳에서 보존한다

출발 배정 때 공용 재고에서 개인·원정 재고로 옮기는 방식과, 귀환 때 순증감만 적용하는 방식 중 하나를 택한다. 양쪽을 섞지 않는다.

예: 탄약 총량 10에서 4를 배정하고, 1을 쓰고, 현장에서 2를 찾아 5를 가져오면 최종 총량은 11이다. 승강장에 올린 뒤 다시 줍는 경우도 소유권 이동이지 신규 획득이 아니다. 시설·간부·조리·공방이 예약한 같은 재료를 다른 곳에서 동시에 소비하지 않는다.

### C07. 시간의 단위를 명시한다

세계 시간, 실제 필드 시뮬레이션 시간, 거리 기반 이동, 정치 회기, 연출 재생 시간을 구분한다. 기한에는 단위를 붙인다. ‘세 구간’인 약속을 화면 전환 세 번으로 세지 않는다. S1의 24구간을 서막 24정차로 옮기지 않는다. [R26]

### C08. 사람과 장소에는 동시 점유 제한이 있다

동일 시간에 같은 인물이 원정·수술 보조·견습 지도·교실·무전 당직에 모두 배치될 수 없다. 역할 겸직은 가능하지만 시간이 겹치는 업무는 안 된다. 큰 솥·식사·교실·의회가 같은 식당칸을 쓰면 일정과 수용 공간을 조정한다. 별도의 분 단위 스케줄러 UI는 만들지 않고 추천·충돌 설명으로 처리한다.

### C09. 사실·관측·전달·믿음을 나눈다

`Fact`는 실제 일어난 일, `Observation`은 누가 직접 알았는지, `Report`는 언제 누구에게 전했는지다. 믿음과 주장에는 출처·확실성·시점이 붙는다. 무전이 울렸다고 살아 있는 송신자가 확인된 것은 아니다. 목격자가 없는 일을 모두가 곧바로 비난하지도 않는다.

### C10. 약속의 대상과 증거를 고정한다

행동·대상·기한·요구 증거를 저장한다. ‘다음 선발권’은 실제 선발 사건이 없으면 이행 완료와 다를 수 있다. ‘다음 회기까지 시작’은 실제 시작 기록을 읽는다. 계속 제공하기로 한 배급은 순간 레버값이 아니라 해당 기간의 제공 기록을 읽는다. 재협상은 옛 약속 삭제가 아니라 새로운 합의 기록이다.

### C11. 사건이 아니라 원인을 해결한다

문제는 `issue_id`, 원인, 피해 당사자·시설, 조짐, 대응, 해결 조건을 가진다. 단열 문제를 해결한 뒤 같은 틈바람 사건은 닫힌다. 이후 연료 부족 때문에 추운 것은 다른 원인이다. 같은 사건 틀을 재사용해도 같은 문제를 다시 만들지는 않는다.

### C12. 시설 정의·인스턴스·가동을 분리한다

정의는 비용·능력·자산 규격이다. 인스턴스는 어떤 객차에 설치된 어떤 장치인가다. 가동은 지금 자원·인력·법 조건을 충족하는가다. 수리 이력은 지속 기록, 현재 성에·불빛·사람 자세는 현재 상태의 표현이다.

### C13. 표현은 결과를 읽고 규칙을 다시 실행하지 않는다

문장·애니메이션·소리·카메라가 같은 사실 ID를 읽는다. 연출을 건너뛰어도 재고·부상·약속은 같다. 잃은 사람의 배경 연기, 없는 식량이 담긴 그릇, 가동하지 않는 장치의 작업음은 막는다. 위험 신호는 장식 효과에 가려지지 않는다.

### C14. 난수·저장·콘텐츠 버전은 재현 가능한 계약이다

현재 정치 이식의 `mulberry32-v1`과 호출 순서를 유지해 같은 결과를 먼저 맞춘다. Godot 기본 난수로 바꾸면 같은 시드가 같은 결과를 보장하지 않는다. 나중에 연출과 규칙 난수를 분리하더라도 명시적 버전 전환으로 한다. 대사·스킨·자국 효과가 추가됐다고 표결이 달라지면 안 된다. [R18][E03]

## 8. 자원·정보·노동을 합칠 때의 핵심 계산

숫자보다 단위와 소유자가 먼저다. 다음 식은 구현 개념이며 확정 밸런스 수치가 아니다.

```text
기말 가용 재고
= 기초 재고 + 실제 생산 + 확정 귀환
  - 실제 소비 - 외부 이전 - 아직 점유 중인 예약

제공 가능한 서비스
= 설비의 가능한 처리량과
  인력·시간·재료·허용된 정책이 충족하는 처리량 중 작은 쪽

남은 작업 시간
= 가용 시간 - 이미 확정한 다른 업무 - 실제 휴식·치료 시간
```

예약은 소비와 다르다. 장부에는 둘 다 있어야 하지만 총량을 이중 차감하지 않는다. 실패한 명령의 예약은 해제한다. 장비를 놓고 도망친 경우에는 재고로 돌아오지 않고 장소 상태에 남는다.

### 8.1 예측과 사실을 구분한 UI

출발 화면에는 ‘현재 석탄’, ‘알려진 경로와 정책을 유지할 때의 소비’, ‘확정된 예약’이 보여야 한다. 아직 모르는 재난을 계산에 넣은 정확한 미래 예언은 하지 않는다. 반대로 이미 약속한 몫을 빼고도 남는 것처럼 표시하면 안 된다.

상대의 표는 확정·예상·변하지 않는 반대를 구분한다. 사망·실종·행방 미확인도 구분한다. 모른다는 것을 숨기기 위해 모두 부정확한 추상 문장으로 돌리지 말고, **확정되는 것은 정확히, 모르는 것은 무엇을 모르는지** 보여 준다.

### 8.2 손실에는 한 원인, 여러 결과, 한 청구 원칙을 적용한다

부상 하나가 의료비·교대·관계·발언에 영향을 주는 것은 좋다. 하지만 같은 부상을 ‘필드 사망 위험’, ‘내정 전문가 위험’, ‘귀환 사고’, ‘스토리 연출’이 각각 다시 추첨하는 것은 다른 문제다.

원인 사실 하나를 여러 모듈이 읽되, 같은 종류의 손실을 두 번 적용하지 않는다. 정치적 반응도 당사자·규칙 위반·공개 기만을 구분해 어느 이유의 반응인지 기록한다. 그래야 플레이어가 결과를 납득하고 다음 계획을 바꿀 수 있다.

### 8.3 효율 개선을 무조건 상쇄하지 않는다

배관·견습·교대·썰매로 얻은 여유는 실제 여유로 남긴다. 난도가 필요하면 미리 예고된 다음 지역·새 목표·선택한 위험으로 확장한다. 모든 개선 직후 비슷한 양의 고장·사고를 자동 생성하면 투자한 의미가 사라진다.

반대로 무한 생산을 허용하자는 뜻도 아니다. 시설은 실제 입력과 공간, 사람을 쓰고 그 조건이 끊기면 멈춘다. **성장의 보상과 성장의 비용이 각각 읽혀야 한다.**

## 9. 문제·사건·연출의 세 층

### 9.1 문제의 상태 기계

```text
원인 존재 → 조짐 → 활성 문제 → 대응 중
                            → 원인 해결 → 후속 정리
                            → 악화 / 다른 문제로 전이
```

원인 해결은 ‘좋은 선택지를 골랐다’가 아니다. 실제 공간·물자·작업·규칙이 조건을 충족한 것이다. 해결 효과가 잠시뿐이면 대사도 임시 대응이라고 말해야 한다.

위생은 이미 예방과 재발 유예를 가진다. 이 원칙을 범용 문제 상태로 확장하되, 기존 위생 수치를 다시 설계하는 변경과 섞지 않는다. [R33]

### 9.2 사건 편집기는 사고 제조기가 아니다

세계 규칙은 실제 소비·부상·기한을 처리한다. 사건 편집기는 그중 플레이어가 판단할 것을 묶는다. 선택권이 없는 보고는 일지나 짧은 음성·장면으로 보낸다.

카드 수가 많다고 실제 결과를 없애지 않는다. 카드 수가 적다고 새 사망이나 배신을 만든다고도 하지 않는다. 같은 원인의 중복 보고는 합치고, 서로 다른 긴급 선택은 명확하게 보여 준다.

필수 내정 4~8분, 강제 결정 1~3개 같은 값은 대표 구간에서 확인할 목표치다. 실제 복합 위기에서 무조건 이 개수에 맞춰 결과를 누락하는 상한으로 쓰지 않는다.

### 9.3 새 디테일에는 ‘왜 지금 보이는가’가 필요하다

사람들이 가방을 풀었다면 생활 안정의 이력이 있어야 한다. 음식을 남겨 뒀다면 실제 몫이 있어야 한다. 다음 담당자가 일을 잇는다면 살아 있고 일할 수 있어야 한다. 조건을 만족하지 않으면 장면이 안 나오는 것이 맞다. 감동 장면을 보기 위해 시스템이 거짓말하지 않도록 한다.

## 10. 매우 어려운 인간찬가를 시스템으로 만드는 법

### 10.1 선한 대사를 고르는 길이 아니라 원칙을 지킬 능력을 만든다

‘같은 사람을 계속 원정에 보내지 않겠다’는 말에는 비용이 있다. 숙련자가 쉬면 다음 작업 효율이 줄 수 있고, 다른 공동체도 위험을 나눠야 한다. 예비 장비·견습·비축·교대 합의가 갖춰지면 그 원칙을 지킬 수 있게 된다.

처음에는 열차장이 무리해서 지킨다. 나중에는 제도와 사람들이 지킨다. 성취의 장면은 큰 연설보다, 늘 원정에 나가던 사람이 이번에는 실제로 쉬고 다른 조가 나가는 모습이다.

> “오늘은 제 차례 아니랍니다.”

### 10.2 인간찬가를 별도 점수로 만들지 않는다

다음은 내부 평가와 콘텐츠 조건에 사용할 수 있는 **증거 묶음**이지 화면에 올릴 새 선함 계기 여섯 개가 아니다.

| 증거 | 무엇을 보나 | 왜 어려운가 |
|---|---|---|
| 생활을 지킬 여력 | 정상적인 배급·난방·돌봄이 실제 제공됨 | 자원과 공간을 지속해서 써야 함 |
| 부담의 분담 | 위험 업무·휴식의 합의와 실제 명단이 일치 | 숙련자를 반복 사용하는 편한 길을 포기할 때가 있음 |
| 대체 가능한 능력 | 한 사람이 쉬어도 지식과 기본 운영이 이어짐 | 견습·매뉴얼·예비 장비가 즉시 수익을 주지 않음 |
| 책임과 정직성 | 약속·보고·권한이 실제 행동과 연결 | 위기를 숨기거나 공을 독점하는 쉬운 정치와 충돌 |
| 이견의 공존 | 반대하는 집단도 같은 규칙 안에서 협력 | 만장일치나 개인 충성만으로 해결할 수 없음 |
| 실패 후 회복 | 잘못을 인정하고 원인을 고쳐 재발을 줄임 | 관계 수치 한 번 복구하는 것보다 오래 걸림 |

한 개 임계값을 넘으면 ‘인간찬가 엔딩’이 켜지는 식은 피한다. 이야기의 결말은 정해진 사건과 실제 이력에서 구성하고, 무한모드에서는 이런 능력이 다음 위기를 버티는 방식으로 계속 드러나게 한다.

### 10.3 반드시 지켜야 할 난도 원칙

좋은 길에는 물자·인력·정치적 대가가 있어야 한다. 그러나 좋은 플레이를 뒷부분의 강제 재난으로 무효화하지 않는다. 여러 준비 방식이 가능해야 하고, 처음 모르는 사실 하나를 틀렸다고 길이 영구히 닫히지 않아야 한다.

사람을 잃지 않는 완벽한 플레이만 인정하지 않는다. 확정된 후위조와 어두운 세계의 불가피한 손실을 없애지 않는다. 그 뒤 누가 책임졌고 무엇을 바꾸었는지가 중요하다. 피해자가 모두 용서할 필요는 없고, 구조한 사람이 모두 유능한 보상 캐릭터가 될 필요도 없다.

강압적 길은 즉시 쓸 수 있는 수단이 있어야 한다. 그렇지 않으면 유혹이 아니다. 다만 정보 왜곡·미뤄 둔 약속·집중된 부담·기술 의존·권한 회수 문제 등 **행동과 연결된 비용**이 남아야 한다. 선한 길을 주기 위해 악한 선택에만 무근거 즉사 벌을 붙이지 않는다.

### 10.4 확인할 대표 시나리오: 빈손으로 돌아온 날

실제 원정이 실패한 경우에만 적용한다. 피해를 일부러 만들어 장면을 강제하지 않는다.

준비가 없는 열차에서는 부족이 곧 새로운 강제 동원으로 이어질 수 있다. 비축·교대·견습·치료 자리를 갖춘 열차에서는 한 번의 실패를 흡수할 수 있다. 사람이 짐을 받고, 준비된 자리를 비우고, 정해진 대행이 업무를 이어간다.

> “먼저 앉으세요. 보고는 듣고 있습니다.”

의회는 이후 원정 판단을 따질 수 있다. 모든 사람이 찬양하지 않는다. 부족한 재고도 그대로 남는다. 다만 **이번 한 번의 실패 때문에 다시 사람을 소모품으로 쓰지 않아도 되는 상태**가 사용자가 만든 결과다.

## 11. 열차의 외관·내관·생활을 누적 기록으로 만든다

### 11.1 선함과 청결을 동일시하지 않는다

열차 표현은 세 층이다.

| 층 | 예 | 갱신 원칙 |
|---|---|---|
| 현재 기능 | 불빛·난방·작업·침상·사용 가능한 통로 | 실제 가동·자원·배치 상태를 읽음 |
| 지나온 이력 | 다른 창틀·덧댄 철판·수선한 가구·남은 그을음 | 실제 설치·손상·수리 사실에 따라 지속 |
| 현재 생활 | 가방 위치·쉬는 사람·공용 식탁·교실·기다리는 자리 | 살아 있는 사람·일정·안정 이력과 공간 제약을 읽음 |

선한 열차도 낡고 그을릴 수 있고, 강압적인 열차도 잘 정비될 수 있다. 인간찬가는 광택이나 따뜻한 색 필터가 아니라 **그 공간에서 사람들이 할 수 있는 행동**으로 보인다.

희생에 따라 UI가 낡는 기존 방향은 별도 표현 계약으로 유지한다. 잠깐 착한 선택을 했다고 과거 흔적이 지워지지 않는다. 반대로 과거의 흉터 때문에 지금 회복된 생활까지 영원히 어둡게 고정하지도 않는다. [R01]

### 11.2 같은 구도에서 달라지는 장면

중요한 객차 몇 곳은 일정한 카메라 구도로 돌아온다. 매번 다른 멋진 컷보다, 같은 자리에 사람이 다시 앉았다는 변화가 기억에 남는다.

창 수리의 보상은 새 창 모델만이 아니다. 추워서 비어 있던 자리에 사람이 돌아오는 것이다. 공방 복원의 보상은 아이콘만이 아니다. 스승이 하던 일을 견습이 이어 하고, 실제로 다른 일을 맡길 여력이 생기는 것이다.

### 11.3 공간의 주소는 객차에 붙인다

모든 소품·생활 장면은 `car_id`와 내부 기준 위치를 사용한다. 객차 순서가 바뀌면 그 사람의 컵·수선 흔적·장치가 같은 객차에 남는다. 보일러 거리처럼 순서에서 파생되는 효과는 새 위치로 다시 계산한다. ‘뒤에서 세 번째 칸’만으로 역사를 저장하면 편성을 바꿀 때 기억이 엉뚱한 객차로 이동한다.

### 11.4 상태 하나를 표현 여러 개가 공유한다

가동된 공방이면 작업물·손동작·작업음이 함께 맞는다. 휴식 시간이면 누운 사람·작업 중지·목소리 톤이 맞는다. 표현마다 별도 난수를 굴려 서로 반대 상황을 그리지 않는다.

모든 주민의 모든 동작을 매 프레임 시뮬레이션할 필요는 없다. 이름 있는 사람과 실제 상황에 걸린 사람은 정확히 표현하고, 군중 연기는 인원·가용성·공간 제약을 지키는 범위에서 추상화한다. 화면 밖의 대표자가 화면 안에서 동시에 쉬고 있는 오류를 막는 것이 애니메이션 종류를 늘리는 것보다 먼저다.

## 12. 파밍 세 번으로 확인하는 통합 사례

다음은 기존 서막을 대체하는 새 정본이 아니라 **S3 통합 검증용 사례**다. 실제 방문 결과에 따라서만 반응을 낸다. 특정 아이템·구조 대상·피해를 반드시 발생시키는 약속은 아니다.

### 방문 1: 술레후프 — 가져온 것이 열차에 남는다

준비 화면은 지금 필요한 연료와 알려진 기회를 보여 준다. 명단에는 실제로 쉴 사람과 직전에 나갔던 공동체가 반영된다. 현장에서는 기존 수색·작업 구역·철수 판단을 한다.

가져온 기술 단서는 복원 조건으로, 상징물은 고유 물건으로, 부상은 같은 인물의 몸 상태로, 현장 결정은 목격·보고로 돌아온다. 부족한 조각은 다음 목표가 되고, 조건이 갖춰진 복원은 공방의 실제 작업을 차지한다.

핵심 검사는 ‘석탄 숫자가 늘었나’가 아니라 **그 선택 때문에 열차의 다음 가능한 행동이 달라졌나**다.

### 방문 2: 구벤 — 전의 약속과 시설이 이번 준비를 바꾼다

첫 방문에서 쉬게 하겠다고 약속한 공동체는 실제 다음 명단에서 확인한다. 그 약속 때문에 숙련이 낮은 대안을 고를 수도 있고, 미리 준비한 장비·정보로 손실을 줄일 수도 있다. 준비하지 않은 어려움을 게임이 공짜로 지워 주지는 않는다.

공방 작업을 마쳤다면 시설은 실제 완성되고, 법 조건에 맞는 효과만 적용된다. 관련 인물이 보고하지 못했다면 대표는 그 사실을 확정적으로 알지 못한다.

### 방문 3: 파이츠 — 개선된 사회가 반복 노동을 다르게 감당한다

같은 연료 작업이라도 작업조 구성·운반·교대·위협 대응이 달라져야 한다. 썰매가 포함된 제작 단계라면 왕복과 무장 공백이 실제로 달라지는지 측정한다. 아직 썰매를 넣는 단계가 아니면 기존 운반으로 검사한다.

충분히 준비한 판은 더 오래 작업하거나, 같은 양을 더 일찍 확보해 조기에 떠날 수 있다. 그 결과를 즉시 다른 재난으로 상쇄하지 않는다. 돌아온 뒤에는 실제 쉰 사람, 지킨 약속, 달라진 시설 이용 장면이 남는다.

### 같은 세 방문을 비교할 정책

생존 물자 우선, 위험 분담 우선, 지식·복원 우선, 강압적 단기 대응을 각각 시도한다. 어느 쪽이 무조건 정답인지 정하기보다 **서로 다른 비용과 다음 선택을 만드는지** 본다. 인간찬가 쪽은 어렵되 가능한 해법이어야 하며, 강압적 쪽은 쉬운 첫 이득과 설명 가능한 이후 비용이 있어야 한다.

## 13. 이야기·대사·인물이 시스템과 충돌하지 않게 한다

### 13.1 보장 사건과 플레이어의 해석을 분리한다

기존 신호 반전과 후위조를 유지한다. 다만 신호를 의심한 열차장과 ‘분명히 생존자가 있다’고 공언한 열차장을 같은 책임으로 취급하지 않는다. 진실은 같아도 **무엇을 알고 무엇을 약속했는지**가 다르다. [R26][R27]

후위조 같은 보장 사건은 어떤 선택을 거쳐 누가 관련되는지의 계약을 가져야 한다. 무조건 최고의 숙련자나 가장 애착 높은 사람을 몰래 골라 잔혹함을 최대화하지 않는다. 기존 확정된 절차·금지선과 후계 구조를 따른다.

### 13.2 인물의 목소리는 성향 이름보다 정보·책임·관계에서 나온다

기관장은 실제 운행과 작업을, 의무장은 치료와 휴식을, 경비대장은 현장 명단과 위험을, 각 대표는 자기 공동체의 부담을 말한다. 같은 ‘거절’도 자신이 아는 사실과 지켜야 하는 관계에 따라 달라진다.

> “데려와 주신 건 압니다. 이 안건에는 반대합니다.”  
> “지난번에도 같은 칸을 보냈습니다. 명단을 다시 보시죠.”  
> “달았습니다. 지금 규칙대로라면 이쪽은 쓰지 못합니다.”

이 문장들은 분위기용 공통 대사가 아니라 각각 구조 이력, 실제 명단, 시설·정책 상태가 있을 때만 나온다.

### 13.3 본문보다 행동이 더 많이 말하게 한다

감사, 원망, 공동체 회복을 모두 카드로 설명하지 않는다. 자리를 비워 주는 행동, 함께 쓰는 공구, 원정에서 제외된 사람의 휴식, 더 이상 올라오지 않는 고장 카드로 보여 준다.

고유한 인물의 죽음만이 기억을 만들지 않게 한다. 살아서 견습을 가르치고, 오랫동안 반대하다 한 안건에만 협력하고, 개인 물건을 제자리에 두는 변화도 같은 제작 밀도로 다룬다. 비극을 일부러 만들수록 특별 콘텐츠를 더 얻는 구조를 피한다.

### 13.4 텍스트 제작 공정

현재 콘텐츠 가이드의 짧은 본문·선택지 규격과 사전 생성·검사 방식은 유지한다. 조건과 효과를 먼저 고정하고 글은 그 위에 쓴다. 런타임 언어 모델에 법·자원·사망 판정을 맡기지 않는다. [R32]

집필 묶음에는 발언자 ID 또는 적법한 역할 대행, 아는 사실, 직전 관계 사건, 감출 수 있는 정보, 현재 시설 상태, 선택 ID, 금지된 사실 진술을 같이 준다. 문체 검사와 사실 검사를 구분한다. 좋은 문장이 잘못된 인물을 말하면 탈락이다.

## 15. 처음 만들 12개와 지금 더하지 않을 것

### 15.1 첫 묶음은 같은 인과를 공유하는 것으로 고른다

D01·D03·D04·D08·D09·D10·D12·D17·D19·D26·D27·D47을 첫 후보로 권한다. 이유는 별도의 거대한 시스템 없이 **인물 ID, 방문 결과, 작업·시설 상태, 약속, 문제 해결**을 공유하기 때문이다.

실제로는 이 12개도 한 번에 다 만들지 않는다. 한 객차, 한 교대 약속, 한 복원, 한 문제 해결을 먼저 고르고 관련 표현만 붙인다. 같은 상태에서 화면·대사·소리·다음 명단이 맞는 것을 확인한 뒤 장소와 인물을 늘린다.

처음부터 D43의 외부 도움 결과나 D45의 세대까지 붙이면 S3의 핵심 원인을 찾기 어렵다. 전체 목표에서 삭제하는 것이 아니라, 결과를 읽을 시스템이 준비되는 순서에 배치한다.

## 16. Godot 구현 방향과 아트 공정

### 16.1 정의 데이터와 런 상태를 나눈다

기술·물건·법·사건의 정의는 공유 가능한 데이터다. 특정 사람의 부상·특정 물건의 위치·특정 약속의 진행은 개별 런 상태다. Godot Resource는 공유 로딩될 수 있으므로, 정의 Resource에 개별 인물의 가변 상태를 써서 여러 인물이 함께 바뀌게 하지 않는다. [E01]

현재 JSON·TypeScript 데이터와 검증기를 모두 버릴 필요는 없다. 정본 정의를 내보내는 경로와 Godot에서 읽는 스키마를 고정하고, 수치를 손으로 두 번 복사하지 않는다. 어느 데이터가 정본인지 파일별로 명확히 한다.

### 16.2 정치 이식은 기존 난수와 계산을 먼저 맞춘다

이미 들어온 `politics/rng.gd` 등의 이식을 출발점으로 삼는다. `s3_record.ts`의 한계는 S1a 중심이라는 것이지, 도구 자체가 쓸모없다는 뜻이 아니다. 기존 표 계산 대조를 유지한 상태에서 내정·약속·귀환을 단계별로 추가한다. [R18][R19]

이식 PR에 재밸런싱·문체 교정·새 콘텐츠·난수 분리를 모두 섞지 않는다. 먼저 같은 입력에 같은 논리 결과가 나오게 한 뒤, 별도 변경에서 재미를 조정한다.

### 16.3 현장 스크립트를 한꺼번에 쪼개지 않는다

필드 진입점에서 필요한 것은 실제 열차의 출발 명세를 받아 쓰고 결과를 내보내는 경계다. 내부 전투·시야·무리·몸 구현을 단지 파일이 크다는 이유로 전면 재작성하지 않는다. 기본 분대와 단독 시험 설정은 테스트 도구로 유지할 수 있다. 제품 경로에서는 실제 명세와 시험용 기본값을 혼동하지 않게 한다. [R17]

### 16.4 저장은 스냅샷과 제한된 이력으로 시작한다

권고는 현재 상태의 스냅샷, 적용한 주요 결과 ID, 진행 중 트랜잭션, 중요한 인물·물건·약속·장소 이력을 함께 저장하는 방식이다. 모든 발걸음과 프레임을 영구 이벤트로 저장할 필요는 없다.

단일 비가역 저장과 내부 복구용 이전 파일은 목적이 다르다. 복구는 마지막 확정 상태로 돌아가는 장치이지 플레이어가 마음대로 선택을 되감는 기능이 아니다. 저장 중 종료·중복 귀환·업데이트 후 이관을 시험한다. Godot의 기본 저장 예제만으로 이 원자성·이관·정확히 한 번 처리가 자동 보장되는 것은 아니다. [E02]

### 16.5 자산 제작의 완료 단위는 ‘작동하는 공간’이다

Tripo 정적 소품은 크기·기준점·재질·팔레트·충돌·상호작용 위치를 맞춰 넣는다. 열차·진입 건물·문·벽 자르기는 모듈 규격을 유지한다. 인물은 공통 뼈대와 자주 보이는 동작의 품질을 먼저 확보한다. [R29]

한 공간의 완료 조건은 다음이다. 같은 시설의 미설치·공사·가동·중단·수리 표현이 있고, 실제 사용자가 배치되며, 작업과 소리와 대사가 같은 상태를 읽는다. 해당 공간에서 일어날 수 없는 장면은 재생되지 않는다.

눈·빛·바람의 높은 품질 목표는 유지한다. 다만 눈 없는 기본 자산과 덮개·재질 변형을 나누는 최신 공정을 따른다. 발자국은 표현용 상태이며 게임 규칙의 새 입력으로 만들지 않는다. 조명·가림·모델이 붙은 실제 S22 장면으로 확인하기 전 성능 통과라고 말하지 않는다. [R25]

## 17. 밸런스·재미를 검증할 때 볼 것

### 17.1 완주율 하나로 인간찬가를 판정하지 않는다

완주율은 필요하지만 충분하지 않다. 같은 위기를 무엇으로 넘겼는지, 이후 어떤 부담과 선택이 남았는지 같이 본다. 고난도 선한 길의 성공률 목표를 이 문서에서 임의의 퍼센트로 확정하지 않는다.

| 질문 | 확인할 기록 |
|---|---|
| 좋은 원칙이 말이 아니라 실행되었나 | 기간별 실제 배급·휴식·교대·치료 제공과 약속 이행 |
| 준비가 실제로 여유를 만들었나 | 같은 조건에서 확보 시간·철수 여유·손실·다음 가용 인원 |
| 실패를 한 번 흡수할 수 있나 | 비축·대행·지식 전수가 있는 판과 없는 판의 회복 |
| 강압이 언제 이득이고 어떤 값을 남기나 | 즉시 물자·표·권한 이득과 이후 정보·관계·부담 이력 |
| 어느 선택이 사실상 항상 정답인가 | 선택별 비용·편익·후속의 조건별 비교 |
| 같은 기능을 여러 메뉴에서 반복 만지나 | 필수 조작 수·되풀이 승인·사람이 읽기 위해 쓴 시간 구분 |
| 시설·사람 변화가 눈에 들어오나 | 설명을 듣기 전 무엇이 달라졌는지 플레이어가 말할 수 있는가 |

### 17.2 같은 조건 비교의 주의

다른 정책이 난수 호출 수를 바꾸면 동일 시드라도 이후 난수열 소비가 달라질 수 있다. 단순히 시드만 같다고 모든 비교가 엄밀한 대조가 되는 것은 아니다. 이식 검증은 현재 알고리즘·호출 순서를 그대로 비교하고, 밸런스 실험은 가능한 공통 시나리오·기록된 입력을 활용한다. 새로운 독립 난수 스트림을 넣을 때에는 규칙 버전을 분리한다.

### 17.3 반복은 변주보다 결과의 누적이 먼저다

같은 사건의 문장을 다르게 쓰는 것만으로 무한모드가 깊어지지는 않는다. 같은 곳을 다시 가는 이유, 이번에는 쉬게 할 사람, 다음에 복원할 장치, 유지하고 싶은 생활을 플레이어가 스스로 목표로 삼는지 본다.

다음 정차가 궁금하지 않으면 새 이벤트 100개를 늘리기 전에 앞선 결과가 다음 준비 화면에 무엇을 남기는지 확인한다.

세 예제를 Node.js의 독립 코드로 실행했다. 읽은 함수의 조건식을 축약해 옮겼으며 저장소 모듈을 import하거나 게임을 실행한 것이 아니다. 계산의 관찰 결과가 예상과 같은지 `assert`로 확인했다.

P01/P02에서 사용한 기술들의 선호와 단계는 읽은 `TECHS`에서 가져왔다. 원문 조건의 관련 부분과 함께 검토할 수 있다. [R07][R08][R09][R13]

```javascript
// Isolated predicates for audit review; not a repository test suite.
const techs = {
  m1: { tier: 1, like: ['medtech'] },
  m2: { tier: 2, like: ['medtech'] },
  w1: { tier: 1, like: ['medtech'] },
  r3: { tier: 3, like: ['medtech'] },
};
const accepted = [{ id: 'w1' }].some(r => techs[r.id].like.includes('medtech'));
const built = { m1: {}, m2: {}, w1: {} };
const selected = Object.keys(techs)
  .filter(id => !built[id] && techs[id].like.includes('medtech'))
  .sort((a, b) => techs[a].tier - techs[b].tier)[0];
// accepted === true; selected === 'r3'; actual restore guard blocks r3.
```

### 20.1 통합 담당이 관리할 최소 장부

기능마다 담당 모듈, 입력, 출력, 다음 소비자, 플레이어에게 보이는 증거, 테스트, 현재 상태를 한 줄로 유지한다. 브리프가 생겼다는 이유로 구현 완료가 되지 않고, 계산 테스트가 있다고 최종 연출 완료가 되지도 않는다.

검증 단계를 다음처럼 구분해 기록한다.

```text
설계 있음 → 계산 코드 있음 → 실행 경로 연결됨
→ 저장·재시도 검증됨 → 플레이어가 결과를 읽음
→ 반복·실기기·콘텐츠 변형에서 확인됨
```

이 문구는 진행 단계 설명이며 별도의 감사 상태 표시를 추가하는 것이 아니다.

### 20.2 병렬 작업의 경계

정치와 필드 담당이 같은 귀환 결과를 서로 계산하지 않게 한다. 아트 담당은 확정된 상태를 읽되 새 효과를 몰래 만들지 않는다. 글 담당은 ID와 사실을 바꾸지 않는다. 새 문서가 생길 때에는 관련 기존 브리프의 문장과 차이를 함께 적는다.

현재처럼 빠르게 여러 작업이 들어오는 프로젝트에서는 ‘설계가 많다’보다 ‘최근에 확정된 선택이 어느 문서까지 반영되었는가’가 중요하다. 자국 추적, 별도 보일러 손잡이, 교실·취사·무전 자리처럼 범위가 바뀐 사항을 먼저 정리한다.

### 20.3 아직 확정하지 않은 것은 명시적으로 남긴다

무전 당직·끊김의 구체 시점과 R1 이전 기본 연락 해석, 음식의 물리 환산과 공개 배급 차이, 썰매 총량 제한의 화면 표현, 반복 위기의 적절한 빈도, 인간찬가의 실제 달성 난도, 캠페인 끝 갈래는 추가 검증·설계 대상이다.

이 보고서는 이를 질문으로 돌려 작업을 멈추지 않는다. 권고안을 제시하되 기존 확정 기록을 임의로 덮지 않는다. 특히 테스트하지 않은 성공률·제작 시간·실기기 성능을 새 기준으로 고정하지 않는다.

## 22. 최종 판단

**지금 필요한 것은 더 큰 기능 목록이 아니라, 이미 있는 기능이 서로에게 실제 결과를 넘기는 방식의 완성이다.**

즉시 고칠 것은 약속의 대상과 후보, 선택 ID, 최신 문서의 충돌이다. 통합할 것은 실제 인물·물자·시간·정보·정차 결과다. 살릴 것은 이미 작동하는 정치·법과 기술·위생·무리·작업의 기반이다. 눈에 보이게 할 것은 사용자가 만든 생활과, 잘 준비했기 때문에 더 이상 발생하지 않는 문제다.

추가 디테일은 48개를 전부 늘리는 방식보다 **한 사람, 한 물건, 한 객차, 한 약속의 이력이 다음 방문까지 살아 있는지**로 평가하는 편이 낫다. 그 한 바퀴가 맞으면 새 장소·인물·이야기를 넣어도 같은 시스템 안에서 의미가 생긴다.

밖은 끝까지 춥고 위험할 수 있다. 열차의 흉터도 남는다. 그 안에서 누군가가 가방을 내려놓고 잠들 수 있게 되는 것, 열차장이 한 번 실패해도 사람들이 서로를 지키며 버티는 것, 열차장에게 반대하는 사람도 같은 열차에 남을 수 있는 것. **그 평범한 장면을 얻기 위해 얼마나 어려운 일을 해냈는지, 플레이어가 설명 없이 알아보게 만드는 방향을 권한다.**
