## 2. 2026-10-07 클라우드 시험 결과

이 스레드의 클라우드 컨테이너에서 설치가 되는지 확인했다.

- npm과 pypi는 열려 있다. 그래서 지금의 웹(TypeScript) 쪽은 그대로 설치·빌드·테스트가 된다.
- GitHub 릴리스 내려받기(Godot 배포 경로)는 프록시가 403으로 막는다.
- Unity 내려받기 서버와 Android SDK 서버는 연결 자체가 안 된다.

즉 **지금 설정 그대로면 클라우드 스레드는 웹 쪽만 만들 수 있다.** Godot이나 Unity로 가면 프로젝트 설정의 클라우드 환경에서 네트워크 허용을 넓혀야 한다. GitHub Actions는 이 프록시를 거치지 않으니 CI 빌드는 따로 된다(공개 저장소라 Actions 사용료도 없다고 알고 있다. 확인 필요).

## 3. 3D인가, 미리 렌더링한 그림인가

엔진보다 먼저 이게 정해져야 하는데, 이건 아트 방향이라 사용자가 정한다. 기본값으로 보는 안은 아래다.

- **캐릭터는 실시간 3D로 한다(추천).** 미리 렌더링한 스프라이트는 방향 8개 × 동작 × 옷 조합으로 그림 수가 폭발한다. 좀보이드도 월드는 미리 그린 타일로 두고 사람은 3D로 바꿨다(Build 41. 로컬 워커 조사 research/field-mechanics-20261007 브랜치 graphics.md 1장에서 확인. 같은 조사는 우리에겐 2D 타일보다 '실제 3D 월드 + 고정 직교 카메라'가 맞다고 본다). Pro 조사의 MakeHuman 옷, 동작 클립, 상하체 합성도 모두 3D 캐릭터를 전제로 한다.
- **배경은 고정 카메라 3D 로우폴리가 기본, 미리 렌더링 타일은 대안.** 한 파이프라인(Blender → 엔진)으로 끝나고 안개·비·조명을 엔진에서 바꿀 수 있다. 미리 렌더링 타일은 폰에서 더 가볍지만 날씨와 시간대마다 그림을 따로 구워야 한다.
- '화면 컨셉과 UI 연출' 스레드의 렌더링 결과를 보고 다시 판단할 수 있다.

**정차 연출 요구(2026-10-07)로 3D는 사실상 정해진다.** 카메라가 옆면에서 앞쪽으로 도는 장면은 미리 렌더링한 그림으로는 못 만든다(영상으로 구우면 상황별 변형마다 영상이 따로 필요하다). 적어도 정차 장면과 캐릭터는 실시간 3D여야 한다. 필드 배경만 미리 렌더링 타일로 두는 길은 남지만, 정차 장면의 역 배경을 3D로 만들면 그걸 필드에도 쓰는 게 자연스럽다.

내리는 장면의 변형이 많아지는 건 엔진보다 동작 수의 문제다. 통째로 다른 동작을 여럿 만들기보다 '기본 하차 동작 + 자세 층(어깨 처짐, 고개 듦) + 짧은 끼어드는 동작(한숨, 멍하니 보기, 어깨 툭)'으로 조합하는 쪽이 싸다. 조합 규칙은 S1a 스레드와 정치 수치 쪽 일이고, 엔진은 상체·자세 층을 섞는 기능(Godot AnimationTree, Unity 동작 레이어)만 있으면 된다. 둘 다 있다.

아래 비교는 '3D 캐릭터 + 고정 카메라, 정차 때만 카메라 이동' 기준이다.

## 4. 안 셋

### 1안. Godot 4 (GDScript) — 추천

- **필드:** 3D 고정 카메라, 내장 내비게이션, 데칼, 깊이·높이 안개가 있다. 볼류메트릭 안개(빛과 섞이는 안개)는 Forward+ 렌더러 전용이라 우리가 쓰는 Mobile 렌더러에서는 안 된다(4.7 문서, 2026-10-07 확인). Mobile은 메시 하나에 데칼 8개까지라, 쌓이는 피·잔해는 질감 층 교체로 간다. 좀비 무리는 MultiMesh와 동작을 텍스처에 구운 방식(VAT, Pro 조사의 OpenVAT가 Godot 출력을 지원)으로 돌린다. 시야·소음은 격자 계산이라 엔진과 무관하다.
- **잉크 번짐 UI:** 화면 요소(Control)에 바로 셰이더를 거는 구조라 ui_motion 조사의 '마스크 + 노이즈' 안을 그대로 옮기기 쉽다. 한글은 동적 폰트로 바로 된다.
- **AI 개발에 맞는 점:** 편집기가 약 100MB 실행 파일 하나이고, 장면 파일(.tscn)이 짧은 텍스트라 코드처럼 읽고 고칠 수 있다. 헤드리스로 테스트와 내보내기가 된다. 라이선스 인증이 없다.
- **기존 코드:** 정치 핵심 로직 약 1,100줄과 그 테스트를 GDScript로 옮긴다. 콘텐츠 검사기, 프로필 생성기, Gemini 문장 생성 같은 도구는 TypeScript 그대로 둔다(게임 밖에서 도는 도구라 옮길 이유가 없다). 콘텐츠는 JSON이라 그대로 읽는다.
- **약점:**
  - 폰에서 3D 성능이 Unity보다 덜 검증됐다. 2026-10-07 조사에서 찾은 Godot 폰 3D 상업 출시작은 작은 인디 둘뿐이고, 근거도 개발자 글과 스토어 목록이라 약하다. 우리 규모의 3D 생존 게임 사례는 없다. 이게 가장 큰 위험이라 S2 성능 시험이 판단 근거다.
  - Pro 조사가 고른 Unity 전용 도구(URP 데칼, Shader Graph UI 샘플, LitMotion 등)는 못 쓴다. 대부분 엔진 기본 기능으로 대신하지만 몇은 직접 만들어야 한다.
  - 에셋 스토어가 작다. 유료 동작 팩(Kubold 등)은 FBX라 들여올 수는 있다.
  - C# 프로젝트는 Godot 4에서 웹 내보내기가 안 되고 iOS는 4.2부터 실험적 지원이다(공식 문서 확인). 그래서 GDScript로 간다.
- **돈:** 엔진 0원(MIT).
- **판:** 최신 안정판은 4.7.2(2026-08-18), 4.8은 개발판이다(공식 다운로드 기록 확인). 4.7.2로 시작한다.

### 2안. Unity 6 (URP, C#)

- **필드:** 폰 3D 성능, GPU 인스턴싱, 동작 시스템, 셰이더 도구가 가장 검증됐다. Pro 조사의 도구 목록을 그대로 쓸 수 있다.
- **잉크 번짐 UI:** Shader Graph UGUI 샘플과 UIEffect로 된다. 한글은 TextMeshPro 동적 글꼴 아틀라스를 따로 설정해야 한다.
- **AI 개발에 안 맞는 점:**
  - 편집기가 플랫폼 모듈까지 수 GB라, 매번 새로 뜨는 클라우드 컨테이너에 설치하기 어렵다. 사실상 사용자 PC(원격 세션이나 로컬 Codex)나 CI에서만 빌드·테스트가 된다.
  - 명령줄 빌드에도 Unity 계정 라이선스 인증이 필요하다. 계정 정보를 비밀 값으로 환경에 넣어야 한다.
  - 장면·프리팹 파일은 GUID로 엮인 긴 YAML이라 AI가 고치면 깨지기 쉽다. 장면 조립은 결국 편집기에서 사람이 하게 된다.
- **기존 코드:** 1안과 같다(핵심 로직을 C#으로 옮기고 도구는 TS로 둔다).
- **돈:** Personal은 최근 12개월 총재정(매출과 투자 포함) 20만 달러 이하만 쓸 수 있고, 넘으면 시제품에도 못 쓴다. Unity 6부터 Personal도 시작 화면 로고를 끄거나 바꿀 수 있다. Pro는 좌석당 월 210달러다(세 가지 모두 공식 페이지 확인, 2026-10-07).

### 3안. 웹 그대로 (TypeScript + Three.js 또는 PixiJS, Capacitor로 앱 포장)

- **기존 코드:** 하나도 안 옮긴다. 테스트도 그대로. 지금처럼 아티팩트 링크로 바로 해 볼 수 있다.
- **잉크 번짐 UI:** ui_motion 조사의 S1 웹 경로(SVG 필터, 국소 WebGL)가 이미 있다. 한글과 화면 배치는 웹이 가장 편하다.
- **약점:**
  - 정차 연출(카메라 이동, 상황별 하차 동작 섞기)을 Three.js에서 전부 손으로 짜야 한다. 동작 섞기 도구와 장면 편집기가 없다.
  - 필드가 문제다. 폰 웹뷰에서 3D 캐릭터 수십 마리 + 안개 + 시야는 중저가 안드로이드에서 버거울 가능성이 높다(불확실, 시험 전).
  - 편집기가 없어서 역 지도, 조명, 동작 연결을 전부 코드로 만든다.
  - 3D를 포기하고 2D 스프라이트(PixiJS)로 가면 성능은 되지만, 3장의 그림 수 폭발 문제가 돌아온다.
- **돈:** 0원.

## 5. 추천과 그 조건

**1안 Godot 4 (GDScript)를 추천한다.** 이 프로젝트는 사람 프로그래머 없이 클라우드 스레드와 Codex가 명령줄로 만든다. 그 조건에서 Unity의 강점(편집기, 에셋, 검증된 성능)은 반쯤 못 쓰고, 약점(설치 크기, 라이선스 인증, 깨지기 쉬운 장면 파일)은 그대로 맞는다. 웹은 정치에는 가장 좋지만 필드가 위험하다.

정차 연출 요구는 추천을 바꾸지 않는다. 컷신 저작 도구는 Unity(Timeline, Cinemachine)가 더 좋지만 편집기에서 손으로 짜는 도구라 이 프로젝트의 만드는 방식과 안 맞는다. Godot은 카메라 경로와 동작 순서를 장면 텍스트나 코드로 적을 수 있다. 3안 웹은 이 요구로 더 불리해졌다.

조건이 하나 있다. **S2의 첫 일을 폰 성능 시험으로 한다.** 회색 역 하나에 좀비 100마리(동작 구운 방식), 안개, 시야 가리기를 넣고, 단면 → 정차 카메라 전환 → 탑뷰로 넘어가는 장면 하나(회색 상자, 하차 자세 두 가지)를 붙여 사용자 폰에서 30fps가 나오는지 본다. 안 나오면 2안 Unity로 바꾼다. 그때까지 옮긴 건 회색 상자뿐이라 바꾸는 비용이 작다.

정치 쪽은 서두르지 않는다.

- S1a·S1b·S1c는 H1, H6 관문을 넘을 때까지 지금 웹(TypeScript)에서 계속 만든다. 아티팩트로 바로 해 보는 속도가 이 단계에선 더 중요하다.
- 정치 로직을 엔진으로 옮기는 건 S3(정차 한 번으로 잇기) 시작 때 한다. 그때는 규칙이 굳어 있어 한 번만 옮기면 된다.
- 콘텐츠 JSON과 스키마를 두 쪽이 같이 읽게 해서, 옮기는 동안 같은 시드로 두 구현의 결과가 같은지 비교하는 테스트를 둔다.

판정: 기준(10분 뒤 30fps 이상, 정차 전환 끊김 없음)과 여유(처음 1분 45fps 이상)를 모두 넘는다. Godot을 그대로 쓴다.

- 여유: 평균 프레임 9ms는 30fps 예산 33.33ms의 약 27%, 60fps 예산 16.67ms의 약 55%다. 가장 느린 프레임도 18.8ms라 30fps 기준에서는 끊김이 안 보인다.
- 열: 61초와 533초 값이 거의 같다. 이 부하로는 S22가 열 때문에 느려지지 않았다.
- 좀비 표시 수는 시야 안·화면 안만 세서 설정 수보다 적다. 배회·추적 계산은 설정 수 전부가 돈다. 실제 게임도 같은 방식으로 그리므로 현실적인 값이다.
- 배터리: 10분에 약 4%(사용자), 한 시간이면 약 24%다. 지금은 프레임 상한 없이 120Hz 화면에 맞춰 약 110fps를 그린다. 실제 게임은 30이나 60fps로 묶어 전력과 열을 줄인다(S2 할 일).

한계(추정 포함):

- 회색 상자다. 전부 3D로 정해진 실제 모델은 텍스처, 재질, 뼈대 애니메이션, 열차 내부가 더해져 더 무겁다. 남은 여유로 보아 감당할 것으로 보지만 확인한 사실은 아니다. 실제 모델 첫 벌이 나오면 같은 HUD로 다시 잰다.
- 정점 3,000 단계(H), 그림자 끔(I), 시야 끔(A~D)은 재지 않았다. 판정에는 필요 없었다.
- 홈 단면과 회의실은 필드와 따로 그리는 장면이라 필드 부하에 더해지지 않는다. 다만 정차 전환처럼 두 장면이 이어지는 순간은 실제 모델로 다시 본다.
- 저가폰 시험은 마감 단계에서 한다.

## 9. 다음 S22 재측정 때 잴 것

첫 실물 모델·지역 키트·달리는 배경이 나오면 한 번에 다시 잰다. 출처는 웹 레퍼런스 수집 r1 2절과 r5·r8(research/reference-harvest-20261007 가지)이다.

- 배포 빌드 기준선(r1 14): 디버그가 아니라 배포 빌드, 같은 장면에서 해상도·그림자·안개를 하나씩 바꿔 잰다. 평균 말고 느린 프레임 분포와 멈춤도 적는다. 프레임 상한 30·60fps도 이때 정한다.
- 적 수별 비용(r1 15): 좀비 16·32·64·128에서 감지·길찾기·애니메이션·그리기를 나눠 잰다. 클라우드 PC 값은 좀비 44마리에 한 걸음 약 1ms라 폰에서 3ms를 넘을 때만 광선 예산·먼 좀비 간소화를 넣는다.
- 앱 중단(r1 16): 전화·화면 잠금·앱 전환에서 저절로 멈추는지(S2 필드판 03c0c0a부터 들어감), 복귀 뒤 가방·부상·이미 뜬 조짐이 그대로인지 본다. 프로세스가 죽는 경우는 저장이 생긴 뒤에 본다(S2 회색 상자엔 저장이 없다).
- 연속 발열(r1 20, r8): 30분 넘게 한 번. 기기·밝기·충전 상태를 적고 처음과 끝의 프레임·입력 지연·메모리를 비교한다.
- 겨울 장면 장시간(r5 2절 18).
- 정차 바깥 장면 세 벌 비교(presentation_motion.md 8b의 C9 v5): 실시간 빛만, 구운 빛 + 높이 안개, 거기에 빛줄기까지. 장면 구성과 판정은 화면 스레드, 만들기와 측정은 S2 몫.
